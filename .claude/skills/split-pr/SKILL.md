# 커밋 분리 + PR 생성 워크플로우

현재 워킹 트리의 변경사항을 리뷰 단위로 쪼개 커밋하고, 푸시 후 GitHub PR을 생성한다.

## 0. 사전 확인

1. `git status --short` + `git diff`로 전체 변경사항 파악. 변경이 없으면 사용자에게 알리고 중단.
2. 현재 브랜치 확인:
   - `dev`/`main`에 있으면 **새 브랜치 생성**. 이름은 `{종류}/{주제}` (예: `refactor/course-read-model`, `feat/notice-v2`, `fix/jwt-expiry`). 주제가 애매하면 변경 내용에서 유추하고, 판단이 어려울 때만 사용자에게 질문.
   - 이미 작업 브랜치면 그대로 사용.
3. **외부 API 불변 검증**: 변경에 `api/` 패키지(컨트롤러, 요청/응답 DTO)가 포함되면 `docs/core/05-api.md`와 대조해 기존 엔드포인트의 경로/요청/응답 스펙이 바뀌지 않았는지 확인. 바뀌었으면 커밋 전에 사용자에게 경고하고 확인받는다.

## 1. 커밋 분리 원칙

변경 파일을 아래 카테고리로 분류하고, **각각 별도 커밋**으로 만든다 (해당 카테고리가 있을 때만):

| 순서 | 카테고리 | 예시 |
|---|---|---|
| 1 | 핵심 로직 (도메인/애플리케이션) | 엔티티, 도메인 서비스, 애플리케이션 서비스, 리스너 |
| 2 | 인프라/영속성 | 리포지토리, QueryDSL, Redis, 외부 클라이언트 |
| 3 | API 레이어 | 컨트롤러, DTO (외부 스펙 불변 확인 후) |
| 4 | 설정 | yml, config 클래스, build.gradle |
| 5 | 테스트 | 새 테스트, 테스트 수정 |
| 6 | 문서 | docs/, README |

추가 규칙:
- 하나의 커밋은 하나의 의도만. 서로 다른 버그 수정은 같은 레이어라도 커밋을 나눈다.
- 리네임/이동과 내용 수정이 섞이면 커밋을 분리한다 (diff 가독성).
- 테스트가 특정 로직 커밋과 강하게 묶여 있으면(그 커밋의 검증 목적) 로직과 같은 커밋에 포함해도 된다. 독립적인 테스트 개선만 별도 커밋.
- **각 커밋은 그 시점에 컴파일이 깨지지 않아야 한다.** 분리가 애매하면 `git add -A` 대신 파일 단위 `git add`로 정확히 스테이징.

## 2. 커밋 메시지 컨벤션

```
[SGMR-X] 한국어 요약 제목 (명사형 종결)

- 무엇을 왜 바꿨는지 본문에 2~4줄 (사소한 변경이면 생략 가능)
- 동작 변화가 있으면 명시

Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>
```

- 제목은 리뷰어가 커밋 목록만 보고 흐름을 이해할 수 있게 작성.
- Jira 티켓 번호를 알면 `[SGMR-X]` 대신 실제 번호 사용 (모르면 X 유지).

## 3. 푸시 전 검증

1. `./gradlew compileJava compileTestJava -q` — 컴파일 확인.
2. 변경된 도메인의 테스트만 선별 실행: `./gradlew test --tests "soma.ghostrunner.domain.{변경도메인}.*"` (Testcontainers 필요 — Docker 미기동이면 사용자에게 알리고 스킵 여부 확인).
3. 실패하면 푸시하지 말고 결과를 보고한다.

## 4. 푸시 + PR 생성

1. `git push -u origin {브랜치}`
2. `gh pr create --base dev` — **베이스는 항상 `dev`** (main 아님).
3. PR 제목: `[SGMR-X] {한국어 요약}`
4. PR 본문 템플릿:

```markdown
## 개요

{이 PR이 하는 일 1~3문장. 외부 API 스펙 변경 여부 명시.}

## 변경사항

{커밋 순서대로 섹션 나눠 설명. 커밋 해시 참조. 표 활용 가능.}

## ⚠️ 배포 유의사항

{런타임 동작이 바뀌는 부분, 마이그레이션/환경변수 필요 여부. 없으면 "없음".}

## 리뷰 포인트

{리뷰어가 집중해서 봐줬으면 하는 부분 1~3개.}

## 테스트

{실행한 테스트와 결과.}

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

5. 생성된 PR URL을 사용자에게 보고하고, 배포 유의사항이 있으면 함께 요약한다.

## 5. 마무리

- `docs/core/06-refactoring-notes.md`에 이번 PR로 완료된 체크리스트 항목이 있으면 `[x]` 갱신을 제안한다 (별도 커밋으로).
- gh 미인증 상태면 사용자에게 `! gh auth login` 실행을 요청한다.
